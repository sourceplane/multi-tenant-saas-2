# cms — architecture

One Next.js 16 application (Payload 3.89.0) built by `@opennextjs/cloudflare`
into `.open-next/worker.js` plus `.open-next/assets`, deployed by the
`cloudflare-worker-turbo` composition. The wrangler config is rendered from
`wrangler.template.jsonc` at deploy time; it declares `main` and `assets`
itself, so the composition's `wrangler deploy` ships the whole build.

```
browser ──► multi-tenant-saas-2-cms-<env> (Worker)       ◄──308── multi-tenant-saas-2-web-console-next-<env> (the old console URL)
              /admin            Payload admin (React, server components): the staff console
              /api/<collection> REST         ┐
              /api/graphql      GraphQL       ├─ payload ─► HYPERDRIVE_CMS ─► Supabase Postgres, schema cms
              /health           liveness + db ┘     │        (cache disabled)
              /api/media/file/* uploaded files      └──────► R2_MEDIA ─► <prefix>multi-tenant-saas-2-cms-media-<env>
              /setup            opens first-admin setup (owner only)
              /auth/lumen/*     the staff Lumen session in, out, and the OAuth return
              /admin/account…   the Lumen account pages (custom admin views)
              /lumen/*          their forms
              /, /courses, …    the academy (learners sign in at /login)
                                     │
        lumen strategy, account pages ──► LUMEN_API (service binding) ─► api-edge ─► identity,
                                                                    membership, billing, notifications
```

## Bindings and secrets

| Name | Kind | From |
|---|---|---|
| `HYPERDRIVE_CMS` | Hyperdrive | `@@wiring(cloudflare-hyperdrive-cms/<env>:hyperdrive_id)@@` |
| `R2_MEDIA` | R2 bucket | `@@wiring(cloudflare-r2-cms/<env>:bucket_name)@@` |
| `ASSETS` | static assets | `.open-next/assets` |
| `ENVIRONMENT` | var | `dev` / `stage` / `prod` |
| `PAYLOAD_SECRET` | secret | `CMS_PAYLOAD_SECRET`, generated by terraform; pushed by `secrets-live` |
| `LUMEN_API` | service | `multi-tenant-saas-2-api-edge-<env>` (stage, prod); who a session belongs to, and sign-out |
| `LUMEN_API_PUBLIC_URL` | var | api-edge's public URL, where the sign-in page sends the browser |
| `LUMEN_API_URL` | var, local only | api-edge over HTTPS when there is no `LUMEN_API` binding (`wrangler dev`) |
| `CMS_SETUP_TOKEN` | secret, optional | the owner's (runbook); absent = setup closed |

## Decisions that shape the code

- **No client-side pool on Workers** (`src/lib/request-scoped-pool.ts`).
  workerd binds a socket to the request that opened it; Payload keeps one pool
  per isolate, and pg-pool would hand one request a client another request
  opened, which hangs. The adapter gets a `pg` whose `Pool` opens a client per
  query or transaction and closes it on release. Hyperdrive pools to Postgres.
- **The schema is not the CMS's to change.** `push: false` at runtime; the
  tables come from `packages/db` migration 200, applied by db-migrate. Each
  collection change is a Payload migration in `payload-migrations/`, converted
  to idempotent SQL by `scripts/payload-migration-to-sql.mjs`.
- **Where the database comes from** (`src/lib/runtime.ts`). Inside the Worker:
  the binding. During `next build`, the payload CLI and local development:
  `DATABASE_URL`.
- **Lumen is the only staff sign-in** (`src/lib/lumen/`, `src/collections/Users.ts`;
  specs/epics/multi-tenant-saas-2-console, after lumen-payload-console). Payload's
  local strategy is off on `users` (`disableLocalStrategy: { enableFields: true }`,
  so the columns stay), so staff have no CMS passwords, and `login`,
  `first-register` and password reset on `users` answer 403. The `lumen`
  strategy reads the `lumen_session` cookie, asks api-edge `GET /v1/auth/session`
  over the service binding (answers cached 30 s per token, keyed by its hash;
  concurrent requests share one lookup; when api-edge cannot answer, a session
  it confirmed in the last 5 minutes still stands until it expires, and an
  unconfirmed one fails closed), and finds, links (by email) or creates the `users`
  row by `lumenUserId`. The token stays in the HttpOnly cookie: it is never on
  `req.user`, so the admin's browser code never sees it. A request that names
  another origin gets no staff user, so no other page can write through the API
  with the cookie, not even a sibling Worker on the same workers.dev site, which
  SameSite does not separate. Every response also carries `frame-ancestors
  'self'` (and `X-Frame-Options: SAMEORIGIN`), so no other page can frame the
  admin and click through it. `/auth/lumen/session` takes a token only from a
  same-origin form post.
- **The account pages are admin views over api-edge** (`src/components/admin/account/`,
  `src/lib/lumen/account-api.ts`, `src/lib/lumen/billing-api.ts`,
  `src/lib/lumen/forms.ts`). Payload's `account` view is replaced, so Payload
  still keeps pending accounts out of it; the others are custom views, which
  Payload does not guard, so each checks for a staff role itself (any of
  admin, editor, instructor) and brings Payload's default template. They read
  per request, uncached, with the person's own token, and render on the
  server: the browser never calls api-edge for them. Forms post to `/lumen/*`
  route handlers that accept only a same-origin post from staff and answer
  `303` back to the page, or, for checkout and the customer portal, to the
  payment provider's https page (the only external redirect). The console's
  framework-free models (`src/lib/lumen/models/`) are copied, not shared: the
  console is retired in LX3.
- **Learners are untouched.** `learners` keep Payload's local strategy, their
  own email and password and the academy's `/login`; their session is a
  separate cookie. Payload asks the `users` strategy first, so in a browser
  holding both, the staff session wins and the academy sees no learner.
- **Roles stay Payload's.** A new staff row has no role: pending, which the
  admin's `unauthorized` view tells them. The first admin needs the owner's
  setup token (`src/lib/setup-gate.ts`, `src/app/setup/route.ts`): while no
  admin exists, the account that signs in with it becomes admin. Admins grant
  the rest: `editor`, `instructor` (with its academies) or `admin`.
- **Media lives in R2, never on a disk** (`src/collections/Media.ts`,
  `src/lib/media-bucket.ts`). `@payloadcms/storage-r2` writes uploads to the
  `R2_MEDIA` binding and Payload serves them back through its access rules. On
  Workers the adapter is always on, and a Worker without the binding fails
  every upload naming it. Off Workers (local `next dev`, the CLI, `next build`)
  it is off and Payload's local disk stands in; with no prefix configured the
  table is the same either way. Uploads over 10 MiB are refused (413), not
  stored truncated: `abortOnLimit` is on.
- **Media belongs to the site or to one academy** (`src/collections/Media.ts`).
  `tenant` is optional: empty is the site's media, which editors manage; set,
  it is that academy's, which its instructors manage. Admins manage all of it
  and are the only ones who delete. `enforceMediaScope` checks the academy
  against what is written, so nobody moves a file out of their reach, and it
  runs before the storage adapter, so a refused upload stores nothing. Files
  are public by URL, like the cover and video URLs courses carry.
- **Pinned versions.** Payload 3.89.0 hashes passwords with 25,000 PBKDF2
  iterations; 3.90.0 hard-codes 600,000, which workerd rejects. Next 16.3.3,
  React 19.2.6, OpenNext 1.20.1 and wrangler 4.116 are the combination Payload's
  own Cloudflare template ships with 3.89.0. `pg` and `pg-cloudflare` are
  direct dependencies and server externals: webpack would otherwise bundle
  pg-cloudflare's empty default export and Postgres connections fail in workerd.
- **Workers Paid.** About 3.8 MiB compressed with the learning app and the R2 adapter (Free allows 3 MiB), and Payload's first request in an
  isolate needs far more than Free's 10 ms of CPU.

## Out of scope here

Learners signing in with Lumen, serving content through `api-edge`, content per
Lumen organization, and image derivatives: resizing, cropping and focal points
need `sharp`, which does not run on Workers, so files are stored and served as
uploaded. Courses keep `coverUrl` and lessons `video_url` as links: media does
not replace them, and video stays a link (10 MiB is too small for it).
